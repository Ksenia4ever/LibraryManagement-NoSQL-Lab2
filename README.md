## 1. Мета роботи

Мета лабораторної роботи — дослідити можливості NoSQL-баз даних, інтегрувати їх у наявну реляційну систему управління бібліотекою та порівняти продуктивність SQL і NoSQL для різних операцій.

Лабораторна робота №2 є продовженням лабораторної роботи №1, у межах якої було реалізовано реляційну базу даних бібліотеки на PostgreSQL.

Основні завдання:

1. Ознайомитися з типами NoSQL-баз даних.
2. Обґрунтувати використання NoSQL у предметній області.
3. Реалізувати документну базу даних MongoDB.
4. Забезпечити відповідність даних PostgreSQL і MongoDB.
5. Провести порівняння швидкодії SQL та NoSQL.
6. Реалізувати базові операції з NoSQL-базою іншого типу.

## 3. Опис предметної області

Система призначена для управління бібліотекою з додатковими послугами.

Вона забезпечує облік:

- користувачів, читачів і працівників;
- книг, авторів, жанрів і видавництв;
- фізичних примірників книг;
- філій бібліотеки;
- видач і повернень;
- бронювань;
- штрафів;
- додаткових послуг та їх замовлень.

У лабораторній роботі №1 було створено 16 взаємопов'язаних таблиць PostgreSQL, реалізовано обмеження цілісності, індекси, Soft Delete, аудит змін, збережені процедури, функції, тригери та представлення.

У C#-застосунку використано патерни Repository та Unit of Work.

У лабораторній роботі №2 цю систему розширено двома NoSQL-базами даних.

## 4. Архітектура системи

Застосунок використовує три бази даних:

### PostgreSQL

Основне джерело інформації про бібліотеку.

Містить 16 таблиць:

- users
- readers
- positions
- branches
- employees
- publishers
- authors
- genres
- books
- book_authors
- book_copies
- loans
- reservations
- services
- service_orders
- fines

Зберігає реляційні зв'язки та забезпечує виконання основних бізнес-операцій.

### MongoDB

Використовується для документного представлення каталогу книг.

База даних: `LibraryNoSqlDb`

Колекція: `book_catalog`

Один документ MongoDB містить інформацію, яка в PostgreSQL розподілена між таблицями:

- books
- authors
- book_authors
- genres
- publishers
- book_copies
- branches

Це дозволяє отримувати підготовлену картку книги одним запитом до документа.

### Redis

Використовується як кеш для карток книг та сховище лічильників переглядів.

Реалізовано:

- кешування документа книги;
- отримання документа з кешу;
- TTL — автоматичне завершення строку життя кешу;
- лічильник переглядів;
- інвалідацію кешу;
- повторне завантаження даних після видалення кешу.

## 5. MongoDB — документна база даних

### 5.1. Модель документа

Для каталогу використовується клас `BookCatalogDocument`.

Приклад документа:

```json
{
  "_id": 1,
  "isbn": "9780451524935",
  "title": "1984",
  "publicationYear": 1949,
  "language": "English",
  "genre": "Dystopia",
  "publisher": "Penguin Books",
  "authors": [
    "George Orwell"
  ],
  "copies": [
    {
      "id": 1,
      "barcode": "BC0001",
      "branchId": 1,
      "branchName": "Central Library",
      "status": "borrowed"
    },
    {
      "id": 2,
      "barcode": "BC0002",
      "branchId": 2,
      "branchName": "Podil Branch",
      "status": "available"
    }
  ],
  "totalCopies": 2,
  "availableCopies": 1
}
```

На відміну від PostgreSQL, автори та примірники зберігаються безпосередньо всередині документа книги.

### 5.2. Синхронізація

Клас `PostgresBookCatalogReader` читає дані з PostgreSQL та формує об'єкти `BookCatalogDocument`.

Клас `MongoBookCatalogService` виконує операції з MongoDB.

Основні методи:

- `UpsertBookAsync()` — створення або оновлення документа;
- `GetAllBooksAsync()` — отримання всіх книг;
- `GetBookByIdAsync()` — пошук книги за ідентифікатором;
- `CountBooksAsync()` — підрахунок документів.

Синхронізація виконується вручну через пункт меню застосунку.

PostgreSQL залишається основним джерелом даних, а MongoDB містить підготовлене документне представлення каталогу.

### 5.3. Перевірка оновлення

Для перевірки синхронізації було тимчасово змінено назву книги `1984` у PostgreSQL на `1984 - MongoDB Sync Test`.

Після повторної синхронізації відповідний документ MongoDB оновився.

Кількість документів залишилася незмінною — 3, що підтвердило відсутність дублювання за ідентифікатором.

Після перевірки початкову назву відновлено та повторно синхронізовано обидві бази.

### 5.4. Індекси MongoDB

У колекції `book_catalog` створено:

- `idx_isbn` — індекс за ISBN;
- `idx_genre` — індекс за жанром;
- `idx_title` — індекс за назвою книги.

Також MongoDB автоматично підтримує індекс `_id_`.

## 6. Redis — база типу ключ–значення

Redis застосовано для кешування карток книг.

При першому зверненні до книги відбувається Cache MISS: документа немає в Redis, тому він завантажується з MongoDB.

Після отримання документ зберігається в Redis на 60 секунд.

Повторне звернення виконується через кеш — Cache HIT.

### Реалізовані операції

| Операція | Призначення |
|---|---|
| GET | Отримання значення з кешу |
| SET | Збереження документа |
| INCR | Збільшення лічильника |
| TTL | Перевірка часу життя |
| DEL | Видалення кешованого запису |

Приклад ключів:

```text
library:book:1
library:views:1
```

Під час тестування підтверджено:

- Cache MISS при першому зверненні;
- Cache HIT при повторному зверненні;
- TTL приблизно 60 секунд;
- збільшення лічильника переглядів;
- видалення кешу;
- повторне завантаження після інвалідації.

Redis використовується як додаткове оперативне сховище, а не як заміна основної бази бібліотеки.

## 7. Тестування швидкодії PostgreSQL і MongoDB

### 7.1. Методика

Для порівняння створено окремий набір із 10 000 тестових книг у кожній СУБД.

У PostgreSQL тестові дані розміщено в окремій схемі `lab2_benchmark` у чотирьох таблицях:

- books
- authors
- book_authors
- book_copies

У MongoDB використовувалася колекція `benchmark_books`.

Дані створено автоматично за однаковими правилами.

Основні таблиці бібліотеки не змінювалися.

Для кожного сценарію виконано:

- 30 прогрівальних повторень кожного типу запиту;
- 5 серій вимірювань;
- 100 операцій у кожній серії;
- обчислення медіанного часу.

Вимірювання виконувалися через C# за допомогою `Stopwatch`.

### 7.2. Сценарії тестування

**Сценарій 1. Отримання картки книги**

У PostgreSQL використовувався запит із JOIN між пов'язаними таблицями.

У MongoDB здійснювалося читання документа за ID.

**Сценарій 2. Підрахунок книг за жанром**

Обидві СУБД виконували підрахунок кількості книг певного жанру.

**Сценарій 3. Отримання 20 книг за жанром**

Виконувалося отримання перших 20 книг заданого жанру, впорядкованих за ідентифікатором.

### 7.3. Результати

Медіанний час виконання операцій:

| Операція | PostgreSQL, мс | MongoDB, мс |
|---|---:|---:|
| Картка книги | 0,6160 | 2,7639 |
| Підрахунок за жанром | 0,5337 | 2,3443 |
| 20 книг за жанром | 0,1642 | 2,3199 |

У всіх трьох сценаріях PostgreSQL показала менший час виконання.

### 7.4. Аналіз результатів

Результати залежать від обсягу даних, типу запитів, індексів, драйверів та локального середовища.

Час вимірювався на рівні C#-застосунку, тому включає не лише роботу СУБД, а й передавання та обробку результатів.

У першому сценарії обсяг отриманих даних між СУБД не був повністю однаковим: MongoDB повертала документ із додатковими полями.

Тому результати характеризують конкретну реалізацію та не доводять загальної переваги однієї технології.

Перевагою MongoDB у цій роботі є можливість зберігати пов'язану інформацію у вигляді одного документа.

Детальні результати 15 серій збережено у файлі:

`Results/lab2_benchmark.csv`

## 9. Встановлення та запуск

### 9.1. Необхідне програмне забезпечення

Для запуску потрібні:

- .NET SDK 10;
- PostgreSQL;
- Docker Desktop;
- Visual Studio або інше середовище для .NET.

MongoDB і Redis запускаються через Docker.

### 9.2. Підготовка PostgreSQL

Потрібно створити базу даних:

```text
Library_management
```

Після цього виконати SQL-скрипт `LibraryDb_full.sql` із лабораторної роботи №1.

Скрипт створює основні таблиці, зв'язки, індекси, процедури, функції, тригери та представлення.

Для локальної конфігурації використовується порт PostgreSQL `5432`.

### 9.3. Запуск MongoDB

У Windows PowerShell:

```powershell
docker run -d --name library-mongodb -p 127.0.0.1:27017:27017 -v library_mongodb_data:/data/db --restart unless-stopped mongo:8.0
```

Перевірка:

```powershell
docker exec library-mongodb mongosh --quiet --eval "db.adminCommand({ping:1})"
```

Очікуваний результат:

```text
{ ok: 1 }
```

Початкове створення бази та колекції:

```powershell
docker exec library-mongodb mongosh --quiet --eval "db.getSiblingDB('LibraryNoSqlDb').createCollection('book_catalog')"
```

Створення індексів:

```powershell
docker exec library-mongodb mongosh --quiet --eval "db.getSiblingDB('LibraryNoSqlDb').book_catalog.createIndex({isbn:1},{name:'idx_isbn'})"
```

```powershell
docker exec library-mongodb mongosh --quiet --eval "db.getSiblingDB('LibraryNoSqlDb').book_catalog.createIndex({genre:1},{name:'idx_genre'})"
```

```powershell
docker exec library-mongodb mongosh --quiet --eval "db.getSiblingDB('LibraryNoSqlDb').book_catalog.createIndex({title:1},{name:'idx_title'})"
```

Якщо контейнер уже існує, для повторного запуску використовується:

```powershell
docker start library-mongodb
```

### 9.4. Запуск Redis

У Windows PowerShell:

```powershell
docker run -d --name library-redis -p 127.0.0.1:6379:6379 -v library_redis_data:/data --restart unless-stopped redis:7.4 redis-server --appendonly yes
```

Перевірка:

```powershell
docker exec library-redis redis-cli PING
```

Очікуваний результат:

```text
PONG
```

Якщо контейнер уже існує:

```powershell
docker start library-redis
```

Обидві конфігурації призначені для локального навчального використання. Не слід відкривати ці екземпляри без автентифікації для зовнішніх підключень.

### 9.5. Налаштування PostgreSQL Connection String

Рядок підключення зберігається у .NET User Secrets.

У каталозі проєкту виконайте:

```powershell
dotnet user-secrets set "ConnectionStrings:PostgreSQL" "Host=localhost;Port=5432;Database=Library_management;Username=postgres;Password=YOUR_PASSWORD"
```

`YOUR_PASSWORD` потрібно замінити локальним паролем PostgreSQL.

Для використання User Secrets проєкт повинен мати налаштований UserSecretsId.

Секрети не повинні публікуватися в репозиторії.

### 9.6. Запуск застосунку

Відкрити проєкт у Visual Studio або виконати:

```powershell
dotnet restore
dotnet build
dotnet run
```

Після запуску відображається меню:

```text
1 - ЛР №1: PostgreSQL + Unit of Work
2 - ЛР №2: PostgreSQL -> MongoDB
3 - ЛР №2: Порівняння швидкодії
4 - ЛР №2: Redis кешування

0 - Вийти з програми
```

Меню працює в циклі `while (true)`, тому після завершення операції можна повернутися до вибору наступної.

Рекомендований порядок першого запуску:

1. Виконати пункт 2, щоб заповнити MongoDB з PostgreSQL.
2. Виконати пункт 4 для перевірки Redis.
3. Виконати пункт 3 для тестування швидкодії.
4. Виконати пункт 1 для демонстрації функцій першої лабораторної.

## 11. Перевірка Redis

Перевірка доступності:

```powershell
docker exec library-redis redis-cli PING
```

Отримання лічильника переглядів першої книги:

```powershell
docker exec library-redis redis-cli GET library:views:1
```

Перевірка TTL кешованої книги:

```powershell
docker exec library-redis redis-cli TTL library:book:1
```

Значення TTL може змінюватися залежно від часу після кешування.

## 12. Особливості та обмеження

- PostgreSQL залишається основним джерелом даних.
- MongoDB зберігає документне представлення каталогу.
- Синхронізація запускається вручну через меню.
- Автоматичне відстеження змін PostgreSQL не реалізовано.
- Redis кешує картки книг на 60 секунд.
- Кеш може тимчасово містити застарілу копію до закінчення TTL або інвалідації.
- Тестування швидкодії проводиться на окремому синтетичному наборі даних.
- Результати вимірювань залежать від локального середовища.

## 13. Висновок

У лабораторній роботі №2 розширено реляційну систему управління бібліотекою двома NoSQL-технологіями.

За допомогою MongoDB реалізовано документний каталог книг, який об'єднує інформацію з кількох реляційних таблиць.

Реалізовано перенесення даних із PostgreSQL до MongoDB та перевірено оновлення наявних документів без дублювання.

За допомогою Redis реалізовано кешування, TTL, лічильники переглядів та інвалідацію кешу.

Проведено експериментальне порівняння PostgreSQL і MongoDB на 10 000 тестових книгах.

За результатами проведених вимірювань PostgreSQL продемонструвала менший час виконання обраних операцій.

Робота показала, що вибір між SQL та NoSQL залежить від структури даних, характеру запитів, вимог до узгодженості, продуктивності та призначення конкретної частини системи.
